# 풀이 커밋 작업

## 범위 선택

먼저 “풀이 파일만 커밋할까요, README 문제 목록도 함께 추가할까요?”라고 묻는다. 선택 UI가 있으면 `파일만`, `파일 + README`를 제공한다. 답을 기다린다. 사용자가 이미 범위를 명시했다면 다시 묻지 않는다. 커밋 작업 선택과 범위 응답은 해당 풀이 파일의 커밋 및 현재 브랜치 push까지의 요청으로 취급한다. 스킬 수정 요청 자체를 실제 풀이 커밋 실행 요청으로 취급하지 않는다.

## 대상 확인

- 작업 전 적용되는 AGENTS.md를 확인한다. `git status --short`, staged/unstaged diff, 현재 브랜치, remote 및 upstream을 확인한다. 새 파일은 내용을 읽는다.
- 기본 대상은 변경·추가된 풀이 소스 파일이다. 에이전트 설정, 임시 파일, IDE 파일 등은 포함하지 않는다. 삭제·이름 변경은 명시 요청 없이 일반 풀이 추가로 처리하지 않는다. 대상이 모호하면 후보를 보여주고 확인한다.
- 파일 경로·주석·본문·기존 기록에서 문제 출처, 정식 문제명, 풀이자를 확인한다. 풀이자는 파일명 또는 주석에서 우선 확인하고 git 작성자를 임의로 대입하지 않는다. 알 수 없는 필수 정보만 묻는다.
- 기존 staged 변경은 보존한다. 파일별 명시적 경로를 사용하고 `git add .`나 `git commit -a`로 전체를 포함하지 않는다. 사용자가 stage해 둔 변경을 몰래 unstage하거나 stash하지 않는다. 부분 stage된 대상은 전체 파일 커밋 의도와 충돌하는지 먼저 확인한다.

## 파일별 커밋

각 풀이 파일을 하나의 커밋으로 만든다. 메시지는 아래 순서이며 마지막 `풀이`는 고정 문구다. 중괄호는 실제 메시지에 넣지 않는다.

```text
{문제출처} {문제이름} {풀이자} 풀이
```

예: `LEETCODE Course Schedule 박재환 풀이`

출처는 기존 표기(BOJ, PROGRAMMERS, SWEA, CODETREE, DOJ, JUNGOL, LEETCODE, SOLVESQL 등)에 맞춘다. 같은 문제의 풀이 파일이 여러 개여도 각각 커밋한다. 성공한 커밋의 실제 포함 경로를 확인한다. 이미 커밋한 파일을 재실행 시 다시 커밋하지 않는다.

## README 포함 모드

루트 README.md에서 현재 월·주차의 활성 문제 목록 영역을 찾는다. 과거 기록 `<details>` 안의 표와 문제 출처 사이트 표는 대상이 아니다. 이 활성 영역의 **첫 번째 문제 표는 알고리즘**, **두 번째 문제 표는 SQL**이다. 문서 전체에서 두 번째 Markdown 표를 고르는 방식은 사용하지 않는다.

- 알고리즘 파일은 첫 번째 문제 표, SQL 파일은 두 번째 문제 표의 끝에 추가한다. 각 표의 마지막 번호 + 1부터 연속 번호를 사용한다. 기존 행의 순서·번호를 바꾸지 않는다.
- 현재 구조에서 SQL 문제 표가 없으면 첫 번째 알고리즘 표 뒤, 과거 기록/출처 영역 앞에 `### SQL`과 동일 열(`번호 | 문제 이름 | 링크`)의 두 번째 문제 표를 만든다. 기존 출처 표나 과거 주차 표를 SQL 표로 변경하지 않는다. 현재 주차를 임의로 보관하거나 새 주차로 넘기지 않는다.
- 문제명과 공식 문제 링크를 넣는다. 링크는 파일 주석·기존 기록·공식 페이지에서 확인하고 추측하지 않는다. 확인할 수 없다면 링크 확보가 필요한 항목을 알리고 README 커밋을 보류한다.
- 동일 문제의 여러 풀이자·여러 풀이 파일은 문제 링크/ID를 기준으로 한 행만 추가한다. 해당 활성 표에 이미 있는 문제는 중복 추가하지 않는다. 과거 주차에 있다는 이유로 현재 표에서 제외하지 않는다.
- 풀이 파일들은 각각 커밋한 뒤 README 변경만 별도 커밋한다. 메시지는 `README 문제 목록 추가`로 시작하고 추가한 문제 범위를 짧게 적는다. 원래 있던 관계없는 README 편집은 포함하지 않는다. 섞여 있으면 필요한 부분만 stage하고 diff를 확인한다.

`파일만` 모드에서는 README를 수정하거나 커밋하지 않는다.

## Push 및 완료 보고

선택 범위의 커밋을 마친 뒤 현재 브랜치의 upstream으로 일반 push한다. upstream이 없고 remote가 하나라면 그 remote의 같은 이름 브랜치를 대상으로 설정해 push한다. 여러 remote 등으로 목적지가 모호하면 질문한다. 다른 기존 로컬 커밋이 함께 push될 예정이면 목록을 보여주고 포함 여부를 확인한다.

force push, 자동 reset, 타인의 변경 삭제를 하지 않는다. non-fast-forward면 원격 상태를 조회하고 충돌/분기 상태를 보고한다. 권한 또는 네트워크 오류로 push가 실패하면 로컬 커밋을 유지하고 성공했다고 보고하지 않는다. 환경이 요구하는 실행 승인은 도구를 통해 요청한다.

완료 시 파일별 커밋 해시·메시지, README 갱신 여부, push한 remote/브랜치와 성공 여부를 간결하게 보고한다.
